Spec-Driven Development Framework

1
Context Dump & Problem Framing Foundation ▼
Prompt — context injection
You are a senior engineer helping me build [FEATURE/SYSTEM NAME].

Tech stack: [e.g. Next.js 14, Postgres, Prisma, Tailwind]
Existing codebase context: [brief description or paste key files]
Constraints: [performance, auth model, deadlines, team size]

Do NOT write any code yet. First, confirm your understanding by restating:
1. The core problem being solved
2. Key constraints you'll respect
3. What success looks like
4. Any clarifying questions before we proceed

Why: Forces explicit alignment before any implementation. Prevents "drift" where Claude solves the wrong problem confidently.

2
Requirements Specification Spec ▼
Prompt — generate spec doc
Now write a formal SPEC for this feature. Use this exact structure:

## Overview — one-paragraph summary
## Functional Requirements — numbered list, each starting with "The system SHALL..."
## Non-Functional Requirements — performance, security, scalability
## Data Model — entities, fields, relationships, constraints
## API Contract — endpoints, request/response shapes, error codes
## Edge Cases & Invariants — what must always be true
## Out of Scope — explicit exclusions

Use precise language. Avoid "should" — use "SHALL" for mandatory, "MAY" for optional.

Why: The SHALL/MAY distinction eliminates ambiguity. "Out of Scope" prevents scope creep during implementation.

Prompt — spec review
Review the spec you just wrote. Identify:
1. Any requirements that are contradictory or mutually exclusive
2. Missing requirements you'd expect for a feature like this
3. Requirements that are under-specified (too vague to implement)
4. Any data model issues (missing indexes, cascade rules, normalization problems)

Then produce a revised SPEC v2 incorporating fixes.

Why: Self-review catches ~60% of spec issues before a single line of code is written.

3
Test-First Design Tests ▼
Prompt — generate tests BEFORE implementation
Based on the spec, write a complete test suite BEFORE any implementation code.

For each functional requirement, write:
1. A happy path test — normal expected usage
2. An edge case test — boundary values, empty inputs, max limits
3. A failure test — what should fail and how gracefully

Use [Jest/Pytest/etc.] with descriptive test names following the pattern:
"given [state], when [action], then [expected outcome]"

Do NOT implement the functions yet — use placeholder stubs that throw NotImplementedError.

Why: Writing tests first forces you to think about the interface before the internals. Prevents tests being retrofitted to match buggy code.

4
Implementation — Spec-Locked Build ▼
Prompt — implement one requirement at a time
Implement ONLY Requirement [#N] from the spec:
"[paste the exact requirement]"

Rules:
— Do not implement any other requirement in this step
— If implementing this requirement requires touching something outside scope, STOP and flag it
— Add inline comments referencing the spec: // SPEC-3.2: validate unique email
— After writing the code, list which test cases from Phase 3 this satisfies

After each requirement, output: "SPEC REQUIREMENT [#N]: IMPLEMENTED ✓"

Why: One requirement per turn prevents Claude from making assumptions about future requirements and avoids over-engineering.

Prompt — cross-check before continuing
Before implementing the next requirement, verify the current state:
1. List every spec requirement and mark it: ✓ Implemented / ⏳ In Progress / ✗ Not started
2. Identify any code written that is NOT traceable to a spec requirement (remove or flag)
3. Confirm all edge cases from the spec are handled in the current code

Only proceed when I confirm.

Why: "Spec traceability" — every line of code maps to a requirement. Eliminates ghost code that causes subtle bugs.

5
Spec Compliance Audit Audit ▼
Prompt — final audit
Perform a complete spec compliance audit on the implementation. For EACH requirement in the spec:

1. Quote the relevant code that implements it
2. State whether it fully, partially, or does not satisfy the requirement
3. Flag any requirement that is implemented incorrectly or with the wrong assumptions

Then check the edge cases section — trace each invariant to a specific guard clause or test.

Output a compliance table: | Req ID | Description | Status | Code Reference |

Why: This table becomes your PR checklist and documentation artifact simultaneously.

6
Adversarial Review Harden ▼
Prompt — attack your own code
You are now a hostile code reviewer. Your job is to find every way this implementation can break.

Attack vectors to check:
— Race conditions: What happens with concurrent requests?
— Input abuse: Null, empty, max-length, unicode, SQL injection, XSS
— State corruption: Partial failures — what state is left behind?
— Performance cliffs: What inputs make this O(n²) or cause a DB full-scan?
— Auth bypass: Can a non-owner access this resource with a crafted request?
— Spec violations: Does any code silently do something the spec forbids?

For each finding: severity (P0/P1/P2), description, reproduction steps, fix.

Why: Adversarial mode bypasses Claude's natural tendency toward optimistic implementation. It finds the things polite review misses.
